# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

All commands assume the repository root unless noted. The root `.env` is the single source of truth for both apps (`vite.config.ts` sets `envDir: '../..'`; the API resolves the nearest parent `.env` in `settings.py`).

```bash
# Full stack (containers)
docker compose up --build -d
docker compose up --build api-server        # single service

# Recommended hybrid: DB in Docker, apps local
docker compose up -d postgres
```

Backend — **run these from `apps/api-server`**: `alembic.ini`, the ruff/pytest config in `pyproject.toml`, and the `src.*` import root all live there, not at the repository root. Requires env vars exported from root `.env` and `DATABASE_URL` pointing at `localhost` (not `DATABASE_URL_DOCKER`); `set -a; source ../../.env; set +a` on a POSIX shell, or the PowerShell loop in the README's local-development section on Windows.

```bash
pip install -e ".[dev]"
uvicorn src.main:app --reload --host 0.0.0.0 --port 8000
pytest                                       # whole suite
pytest tests/test_payments.py::test_name -v  # single test
ruff check .                                 # line-length 100
alembic upgrade head
alembic revision --autogenerate -m "describe_change"
python -m src.infrastructure.tasks.bootstrap_db --seed [--force-seed]
```

Frontend (`apps/web-client`):

```bash
npm run dev -- --host 0.0.0.0 --port 5173
npm run typecheck    # vue-tsc -b — the only automated frontend gate (no tests, no ESLint)
npm run build        # typecheck + vite build; build:ci skips typecheck
```

Dev URLs: web `:5173`, Swagger `:8000/docs`, health `:8000/health`. Default dev admin is `admin` / `admin123`.

## Architecture

Monorepo: `apps/api-server` (FastAPI + SQLAlchemy 2.0, Python 3.12), `apps/web-client` (Vue 3 + Vite + TS), PostgreSQL 16.

### Backend layout — where code actually lives

The tree contains clean-architecture placeholder packages (`src/application/`, `src/domain/entities/`, `src/domain/rules/`, `src/domain/value_objects/`, `src/api/v1/routes/`) that are **empty**. Real code is in:

- `src/modules/<domain>/` — one package per domain (`authentication`, `customers`, `loans`, `collateral`, `payments`, `finance`, `reporting`, `settings`, `backup`), each with `router.py` (routes + business logic inline) and `schemas.py` (Pydantic). Business logic mostly lives in the routers; the extracted service modules are under `finance/` — [interest_generation.py](apps/api-server/src/modules/finance/interest_generation.py), [interest_balance.py](apps/api-server/src/modules/finance/interest_balance.py), [penalties.py](apps/api-server/src/modules/finance/penalties.py), [allocation.py](apps/api-server/src/modules/finance/allocation.py), [loan_status.py](apps/api-server/src/modules/finance/loan_status.py) — and under `backup/`: [service.py](apps/api-server/src/modules/backup/service.py) (export), [restore.py](apps/api-server/src/modules/backup/restore.py), [schedule.py](apps/api-server/src/modules/backup/schedule.py), [runner.py](apps/api-server/src/modules/backup/runner.py), [destinations.py](apps/api-server/src/modules/backup/destinations.py) and [google_drive.py](apps/api-server/src/modules/backup/google_drive.py). `reporting` has no `schemas.py` — its four `/reports/*` endpoints return plain dicts.
- `src/infrastructure/persistence/models.py` — **all** SQLAlchemy models in one file.
- `src/domain/enums/` — `LoanType`, `LoanStatus`, `UserRole` only.
- `src/shared/dependencies/` — `get_db`, `get_current_user`, `require_roles(*roles)`.
- `src/api/v1/router.py` — aggregates module routers under `/api/v1`.

Routers carry their own prefix (`/customers`, `/payments`, `/collateral-items`, `/reports`, `/settings`); `authentication`, `loans`, and `finance` declare no prefix and spell paths out (`/auth/login`, `/loans`, `/loan-applications`, `/interest/generate`, `/loans/{id}/balance`, `/loans/{id}/ledger`).

There is **no `users` module** — user management (`GET/POST/PUT /users`) lives in [authentication/router.py](apps/api-server/src/modules/authentication/router.py) alongside login, refresh, and the forgot/reset-password pair.

**Password recovery answers identically whether or not the account exists** — same 200, same message, and `reset_token`/`reset_token_expires_at` are only written when the user is found *and* active. `POST /auth/reset-password` collapses "no such token", "expired" and "inactive user" into one 400 for the same reason. Do not turn an unknown identifier into a 404 or split those messages: telling a caller which usernames exist is the thing this endpoint is built to withhold. **The guarantee is about timing as much as wording**, which is why the email is handed to FastAPI's `BackgroundTasks` and never awaited: sending inline made a matching identifier cost an HTTPS round trip to the mail provider and an unknown one cost nothing, answering by the clock the question the identical message refuses to answer in words. A mail failure must never reach the caller either — "the provider is down" is itself a statement that there was an address to write to. The token still comes back in the response body **only when `APP_ENV != "production"`**, and that matters more now rather than less: an installation with no mail credentials is a supported state, and the response is the only way the flow can be finished there. Tokens live 15 minutes and are cleared on use. Full spec in [docs/password-recovery.md](docs/password-recovery.md).

**Outbound mail is [infrastructure/email/](apps/api-server/src/infrastructure/email/), split into a transport and a message.** [client.py](apps/api-server/src/infrastructure/email/client.py) knows how to send *a* message and nothing about any flow; [password_reset.py](apps/api-server/src/infrastructure/email/password_reset.py) owns what this one says. A second kind of mail adds a module beside the second, not a branch inside the first. Three things are decisions:

- **`send_email` raises on every failure** — missing configuration, a rejected token, a timeout. The first version logged and returned, so a reset that never arrived looked exactly like one that did: the operator was told to check their inbox and nothing was coming. Only `send_password_reset_email` swallows, and only because a background task that raises dies where nobody sees it.
- **There is no from-address setting.** `V1SendRequest` has no `from` field — the sender is whichever mailbox `HOSTINGER_MAILBOX_RESOURCE_ID` names, and the token must be authorised for it. Only the display name is ours. A `MAIL_FROM_ADDRESS` setting existed, looked like it chose the sender, and did nothing. The mailbox id is an opaque `AC…` value from `AccountApi.get_current_account()`; a plausible placeholder like `"me"` is refused with **403, which is indistinguishable from a revoked token** — that is what the failure message spells out so the next person does not re-diagnose it.
- **Locale comes from the client first, the `Accept-Language` header second, Spanish last** (`normalise_locale`), and the header is parsed by its first tag's *primary subtag*. A substring search finds `"en"` inside `fr-ES` and writes to a French speaker in English. The web client sends the interface locale the operator chose and we stored, which is not necessarily what their browser reports.

Adding an endpoint: new route in the module's `router.py` + schemas in `schemas.py`; a role dependency on every route; `write_audit(db, ...)` from [shared/utils/audit.py](apps/api-server/src/shared/utils/audit.py) after any financial or collateral mutation (it commits).

**Who may call what** — `UserRole` is `administrator` / `loan_officer` / `collector`, and the split is a policy, not an accident:

- `require_roles(administrator)` — user management, `PUT /settings`, and the whole `backup` module.
- `require_roles(administrator)` also covers **disposing of a pledge** — `liquidate` and `sell`. Writing off or selling someone else's goods is not the same decision as lending against them.
- `require_roles(administrator, loan_officer)` — everything that creates or changes credit: loan create/update/delete/renew/close/foreclose, application approval, customer writes, registering and editing pledges, and **all four `/reports/*`** endpoints.
- `require_roles(administrator, loan_officer, collector)` — reads, the payment-taking routes, and **handing a pledge back** (both `release` routes): the collector is who stands at the counter, and `_assert_loan_fully_settled` is what makes it safe — they can only release pledges the system has already decided are free. A collector still cannot open a loan, register a pledge or pull a report.
- The `finance` module is the deliberate exception: `/interest/generate`, `/loans/{id}/balance` and `/loans/{id}/ledger` take plain `get_current_user`, so any authenticated role can trigger a generation cycle. `GET /settings` and the collateral read routes are the same.
- **The system must always keep one active administrator.** `PUT /users/{id}` flushes, counts, and refuses with 400 if the change would leave none — creating users is itself admin-only, so an installation with no admin can never get one back from inside the application. The backup restore refuses an archive for the same reason.

**Loan applications are an API-only surface.** `POST/GET /loan-applications` and `/loan-applications/{id}/approve` exist and write audit rows, but nothing in the web client references them — the frontend creates loans directly, and `Loan.application_id` is nullable and stays `NULL`. Approval sets a varchar `status` and stamps `reviewed_by`/`approved_by`; it does **not** create the loan. Don't assume an approval gate exists in front of loan creation.

### Startup side effects

[main.py](apps/api-server/src/main.py) on startup calls `assert_production_secrets`, which **refuses to boot when `APP_ENV=production` still carries `JWT_SECRET_KEY=change_this_in_production`** — it is printed in the README and in `.env.example`, so anyone can mint a token for any user. Only the literal default is rejected, so an installation that set its own value is unaffected. `ADMIN_PASSWORD` is deliberately **not** checked: it only seeds the admin on first boot, after which the password lives in the database and the operator changes it from the users screen, so the variable goes stale by design. Guarding it took a production deployment down over a stale value whose admin had long since set a strong password — and it was blind to the case that matters, a strong variable over a weak stored password. **Only put a value in this guard when it is both genuinely unsafe to serve with and fixable from the environment alone**; anything else belongs in a log line, not in a check that can stop a deployment. It then runs `alembic upgrade head` + `init_database()` when `DB_INIT_ON_STARTUP`, and starts two in-process thread schedulers: interest generation when `AUTO_INTEREST_GENERATION_ENABLED`, and the recurring backup when `BACKUP_SCHEDULER_ENABLED`. The backup thread only reads the clock — whether a copy is ever taken is the schedule stored in the database, which is off until an administrator turns it on.

**That in-process `alembic upgrade head` is why [alembic/env.py](apps/api-server/alembic/env.py) must keep `fileConfig(..., disable_existing_loggers=False)`.** `fileConfig` defaults to `True`, which switches off every logger configured before it runs — and `env.py` is not only executed by the CLI: `run_database_migrations()` imports it into the running API after uvicorn has set up its own logging. With the default, production served every request with `uvicorn.access` silenced, so there was no request log at all, and a login that never reached the server was indistinguishable from one the server rejected. Access logging is not decoration here: the browser is the only other witness, and it reports both as the same error.

**The initial migration is `Base.metadata.create_all`**, so a *fresh* database gets every current model column at revision `0001` and the later `ADD COLUMN` migrations are no-ops on it. They only do work on a database that already exists at an older revision — production. That is why every schema migration here uses `IF NOT EXISTS`, and why testing one properly means `alembic downgrade` to before it and then upgrading, rather than starting from an empty database where it would pass trivially. `init_database()` takes a PG advisory lock so multiple workers can't race on enum creation/seed. Bootstrap never overwrites the admin password unless `ADMIN_PASSWORD_RESET_ON_STARTUP=true`.

Every uvicorn worker starts its own scheduler thread, so `run_interest_generation_cycle` guards itself with `pg_try_advisory_lock(INTEREST_CYCLE_LOCK_ID)` and silently skips the cycle when another worker holds it — nothing at the DB level rejects a duplicate billing period, so losing that lock means double-charging customers. `interest_cycle_lock(db)` in [interest_scheduler.py](apps/api-server/src/infrastructure/tasks/interest_scheduler.py) is a context manager that **takes the lock on a connection of its own**, held for the whole block; `POST /interest/generate` and the backup restore use the same helper and the same lock id. That connection is the fix, not a detail: `pg_try_advisory_lock` is *session* level — it lives on the connection — and the lock used to be taken on the caller's `Session`, which hands its connection back to the pool on **every commit**. The cycle commits up to three times, so any request that checked that connection out in between left the release running somewhere else, returning `false` where nobody read it, and the lock stayed on a pooled connection permanently: from then on every worker logged "another worker is already running it", `POST /interest/generate` answered 409, and nothing was billed until the process restarted. It short-circuits to "acquired" on non-PostgreSQL dialects so the SQLite test suite still runs.

### Financial model — the core invariants

Two-table payment record: `Payment` is the money received; `PaymentEvent` is the append-only allocation ledger (`payment_type`, optional `interest_charge_id`, per-bucket allocations). Reversal is explicit and flagged on both rows (`Payment.is_reversed` and `PaymentEvent.is_reversed`), never a delete.

**"Deleting" a payment means reversing it.** There is no `DELETE /payments/{id}` and there should not be — the ledger is the evidence of what was collected and given back. `POST /payments/{id}/reverse` requires a `reason` (min 3 chars) and stamps `reversed_at` / `reversed_by` / `reversal_reason` on the row, because the audit table has no read path in the application: without those columns you could see that money had been taken back but not by whom, when, or why. The reversal restores principal **per ledger row**, not from `Payment.allocated_to_principal` — one payment can pay down several loans, so crediting the flat total to `Payment.loan_id` over-restored that loan and left the others short. Only loans whose principal this reversal put back above zero are reopened.

**`PUT /payments/{id}` corrects how a payment was recorded, never how much money it moved.** `PaymentUpdate` carries only `payment_date`, `payment_method` and `notes`, and the endpoint copies them onto every `PaymentEvent` of that payment, found **by `payment_id`**. The amounts used to be editable and reached `Payment` without reaching the ledger they are derived from: a collection of 100.000 spread over two billing periods, edited to 50.000, left the receipt saying 50.000 while the debt stayed reduced by 100.000. The ledger rows were located by matching six fields against their exact old values, so a payment split across periods matched more than one row and updated none of them. A wrong amount is corrected by reversing and re-collecting. `POST /payments` still writes no ledger rows at all and no view calls it (`platformStore.createPayment` is dead code) — it is the remaining way to record money the balances cannot see.

**A `closed` loan can still owe interest.** `pay_principal` closes a loan the instant its principal hits zero, so a payment made with `allow_with_unpaid_interest` leaves a closed loan with live `InterestCharge` rows. `pending_interest_for_customer` therefore includes closed loans *that still owe*, and `principal-context` carries them so printed balances report the real figures — it used to filter every closed loan out, which made that debt uncollectable (absent from the interest screen and from allocation) and made the receipt print "settled in full, nothing pending" over a live debt. Closed-and-settled loans stay excluded, which is what keeps history out of the collection views. Consumers that act on principal (the payment tab, `_resolve_principal_targets`) filter on `outstanding_principal > 0` rather than on status.

**Every read of pending interest must go through [interest_balance.py](apps/api-server/src/modules/finance/interest_balance.py)** — it is the single canonical calculation, shared by the collection endpoints, `Loan.interest_due` and the overdue transition job. It derives balances from non-reversed `PaymentEvent` rows against `InterestCharge.amount`; `InterestCharge.status` is a denormalized cache (kept in sync by `sync_interest_charge_statuses`) and must never be treated as the source of truth. Do not add a second inline pending-interest computation — that divergence was a live bug.

- **Interest accrual**: monthly `InterestCharge` rows anchored on `loan.disbursement_date`'s day-of-month, amount = `principal_base * monthly_interest_rate / 100`, where `principal_base` is the principal the period actually carried — `outstanding_principal` plus every non-reversed principal allocation dated *after* `period_end`, stored on the row. It equals today's balance while the cycle runs on time, so nothing changes in the normal path; with the scheduler stopped for three months over a 700.000 repayment on a 1.000.000 loan, all three backlogged periods used to be billed on the remaining 300.000, two of them at a third of what was owed. Rows generated before this carry `NULL` — what they were billed on cannot be reconstructed after the fact. Generated on loan creation (if disbursement is in the past), by the scheduler, and via `POST /interest/generate`. `GlobalSettings.interest_generation_lead_days` (default 10) is added to "today" so upcoming periods appear early. Existing `(period_start, period_end)` pairs are never duplicated.
- **Interest accrues while the debt is alive, and `overdue` is alive.** Generation runs over `ACCRUING_STATUSES` (`active`, `overdue`) from [interest_generation.py](apps/api-server/src/modules/finance/interest_generation.py) — import it, never re-spell the filter, because the scheduler and `POST /interest/generate` drifting apart is what caused this. It used to run on `active` only, so the cycle that flagged a loan `overdue` was the last one to bill it: a customer five months behind kept a debt frozen at the two months billed before the transition, the arrears reports understated exactly the worst-off customers, and the backlog landed in one lump the day that loan returned to `active`. `closed` and `defaulted` stay out — a settled loan has nothing to bill, and foreclosing is the decision to collect through the pledge rather than through more interest.
- **A charge of amount 0 with status `not_billed` is a month that was deliberately never billed.** Those rows were inserted once, by [migration 0010](apps/api-server/alembic/versions/20260727_0010_close_unbilled_periods.py), for the holes the `active`-only defect left behind: deploying the fix over them would have billed every skipped month at once. Marking them keeps the generator self-healing (a gap that appears *after* this is still filled on the next cycle) while closing the old ones, because "skip periods that already exist" is what holds them shut. `sync_interest_charge_statuses` skips zero charges so the marker survives, and balances drop anything with nothing outstanding, so they reach no screen and no printed statement.
- `generate_missing_interest_charges(db, loans, ...)` only adds, and does it for a whole batch in a fixed number of queries — the cycle used to issue a lookup per loan and then reload every charge it had just committed (the audit summary read the amounts back *after* the commit that expired them), so 40 loans cost 213 queries inside the window where the cycle holds its lock; it is now 15 regardless of portfolio size. Audit summaries are built **before** the commit they describe.
- `recalculate_interest_charges_for_loan` (used by `PUT /loans/{id}`) may only touch periods that have **not** been invoiced. A period is invoiced — and therefore immutable, never rewritten and **never deleted** — when its `period_end` has passed, it has linked `PaymentEvent`s, its penalty has been frozen (`penalty_applied_at`), or it is a zero-amount `not_billed` marker. Editing the disbursement date re-anchors every period, and this used to delete each old charge that carried no payment: a two-day correction wiped three periods and the 4.500 of late penalties already frozen on them, resetting `penalty_applied_at` to `NULL` so they were recomputed months later against today's balance and today's rate — the exact thing [penalties.py](apps/api-server/src/modules/finance/penalties.py) exists to prevent — and it deleted the migration-0010 markers, so those months were billed all over again. Only periods still in the future and untouched may move, and a new anchor never bills a stretch of time an existing invoice already covers. It used to overwrite every due period with the current principal and rate, so correcting a pledge description turned a charge of 50.000 the customer had already paid into one of 30.000 while the ledger still held 50.000. `LoanUpdate` therefore has every field optional: a required `monthly_interest_rate` and `status` meant the form resent the whole loan on every edit and triggered the recalculation each time.
- **Grace days are portfolio policy, not a loan property.** A charge's due date is `period_end + grace_days`, where grace comes from `GlobalSettings.default_grace_days` via `grace_days_for_loan()`. It used to come from `Loan.due_day`, which the create form filled with the *day-of-month of the disbursement date* — so a loan signed on the 25th silently got 25 days of grace and one signed on the 3rd got three. `due_day` is still stored and kept aligned with the setting on create/update/renew, but nothing reads it for penalties. A loan with `late_penalty_rate == 0` gets **zero** grace: grace only postpones the penalty, so on a penalty-free loan it would just park the debt as "upcoming" and hide it from the collection screens.
- **The late penalty is a stored fact, not a formula.** `freeze_due_penalties` in [penalties.py](apps/api-server/src/modules/finance/penalties.py) writes `InterestCharge.penalty_amount`, `penalty_rate_applied` and `penalty_applied_at` **once**, when the period crosses its due date, and every reader takes them as given — `interest_balance.py` reads the column and must never recompute it. It used to be `pending interest x rate` evaluated on every read, so the same debt reported different figures on different days: a partial payment shrank the base it was derived from, raising `default_grace_days` moved every past due date forward and erased the penalty from the whole portfolio backwards, and lowering a loan's rate rewrote penalties on periods that had fallen due months earlier — none of it leaving a trace. Policy changes now reach the periods that fall due after them, and nothing else. `penalty_applied_at` is the **due date**, not the day the cycle ran, so a scheduler running late does not make the penalty look late; `NULL` on all three means the period is still open. The freeze runs in the interest cycle, in `POST /interest/generate` and in `create_loan` (a backdated disbursement is born already past due), and it starts with a `db.flush()` because sessions run with `autoflush=False` and charges the caller just generated would otherwise be invisible to it. **A `defaulted` loan is skipped**, for the same reason `ACCRUING_STATUSES` leaves it out: a penalty is more interest by another name, and foreclosing is the decision to collect through the pledge instead. `closed` loans are not skipped — one settled with `allow_with_unpaid_interest` still owes, and that debt is collected at the counter like any other.
- **One charge per billing period is enforced by the database** (`uq_interest_charge_period` on `loan_id, period_start, period_end`). The advisory lock only makes the collision rare: `POST /interest/generate` used to run without it while the scheduler held it, both read "period missing", both inserted, and customers were billed — and in two cases paid — twice. The endpoint now takes the same lock and returns 409 when the cycle is already running, but the constraint is what makes the duplicate impossible.
- **Interest payments are always allocated oldest-charge-first** — selection hints from the client are accepted but deliberately ignored ([payments/router.py](apps/api-server/src/modules/payments/router.py)). Within a charge: penalty before interest. Leftover money becomes an `interest_advance_payment` event with `interest_charge_id = NULL`.
- **An advance belongs to the customer, not to the loan it was filed against.** A `PaymentEvent` needs a loan, so the row lands on one — but `_net_customer_book` pools advances across every loan of **one** customer and consumes them oldest-due-date-first *across that customer's loans*, never further. The batch handed to it routinely spans the whole portfolio — the penalty freeze, the overdue transition job and `/reports/overdue-loans` all net every loan they are looking at in one call — and a single global pool meant one customer's credit silently settled another's period: the second customer's late penalty was frozen at **zero permanently** (`penalty_applied_at` is what stops it being re-evaluated), their loan never turned `overdue`, and they disappeared from the arrears report, while their own collection screen still showed the debt. The netting used to happen inside the single loan holding the row, so a customer with loans #7 and #12 who paid 200.000 ahead had it all parked on #7: a month later #12 was billed, found no advance of its own, went `overdue` and started accruing a penalty while the customer's own money sat unused next door — the statement reading "200.000 in credit" and "50.000 overdue" at the same time. `available_advance_balance` is still reported per loan so summing it across a customer gives their one credit balance. Expanding to the whole book costs three extra queries and `Loan.interest_due` evaluates this per row of a listing, so `_customers_hold_advances` checks first with one indexed lookup: with no pool to share, per-loan arithmetic gives the identical answer. `sync_interest_charge_statuses` derives from the netted balance too, so a period covered by an advance caches as `paid` — but the cycle does not call it, so a charge born already covered keeps a stale status until the next collection. That is tolerable only because the status is never the source of truth.
- **Money paths take a row lock before they read a balance they are about to act on** — `lock_loans` / `lock_customer_loans` in [locks.py](apps/api-server/src/modules/finance/locks.py), used by `pay_principal` (its targets), `pay_interest` (the customer's whole book, since allocation and the advance pool span it) and the foreclosure sale. Two cashiers taking 100.000 each against a 100.000 principal both read the same figure, both passed the capacity check, and `max(0, ...)` absorbed the negative: two payments recorded, the loan closed, 100.000 of overpayment accounted for nowhere. Rows are locked in id order so concurrent requests queue instead of deadlocking, and the helper short-circuits on SQLite exactly as the interest-cycle advisory lock does. There is still **no idempotency key**, so a double-clicked submit is two payments.
- **On a money path, `write_audit(..., commit=False)`** so the audit row shares the transaction with the money. It commits by default, which is right for a settings change; on `pay_interest`, `pay_principal` and the reversal it meant a second transaction that could fail while the payment stood, leaving a collection nobody appears to have taken. `delete_loan` has always done it this way. `test_audit_transaction.py` pins the row for each path.
- **Principal payments** are blocked while accrued interest is unpaid unless `allow_with_unpaid_interest`, can't exceed `outstanding_principal`, and auto-close the loan at zero. "Accrued" means the period has **ended** (`period_end <= payment_date`): `interest_generation_lead_days` bills the month in progress on purpose so it shows on the collection screen early, and blocking on it refused a customer their own principal payment over interest for days that had not happened yet. The block uses the canonical items, not the API adapter, because it needs `period_end`. `POST /payments/principal` takes either `loan_id` (one loan) or `customer_id` + `selected_loan_ids` / `pay_all_outstanding`, and spreads the money over the targets oldest-disbursement-first, one `PaymentEvent` per loan under a single `Payment`. Two deliberate asymmetries with interest: **the client's loan selection is honoured** (an operator settling a specific loan must not have the money sent elsewhere), and there is **no advance pool** — money that cannot be fully applied is a 400, validated up front so a rejected payment writes nothing.
- **`active` ↔ `overdue` is automatic**, owned by `refresh_overdue_loan_statuses` and run inside the interest cycle (scheduler and `POST /interest/generate`). `closed` and `defaulted` are terminal states set only by explicit operator actions; the job never touches them.
- **Renewal** (`POST /loans/{id}/renew`) moves a live debt to a new row: it inserts a *new* `Loan` whose `principal_amount` and `outstanding_principal` are the source's outstanding, `disbursement_date` is today (so the interest anchor day moves), and `renewal_of` points back at the source. `monthly_interest_rate`, `late_penalty_rate` and `description` are inherited (rate overridable in the payload); the source's `in_custody` pledges are **reassigned to the new loan**, because a pawn loan whose pledges point at a closed row has no security recorded against the debt anyone is collecting. The source is then closed **with `outstanding_principal` set to zero** — it used to keep its full outstanding while closed, and since `principal-context` reports anything that still owes, one 1.000.000 loan renewed once showed the customer owing 2.000.000 on the collection screen and on the printed statement, while `_resolve_principal_targets` refused to collect the closed half. Interest already accrued stays on the source and is collected from the interest screen. A `closed` loan cannot be renewed again.
- **Foreclosure** (pawn loans only) sets `LoanStatus.defaulted` and flips `in_custody` collateral to `for_sale`. `POST /collateral-items/{id}/sell` then applies the proceeds through [allocation.py](apps/api-server/src/modules/finance/allocation.py) exactly as a counter payment would — penalty, then interest, oldest period first, then principal — writing one `PaymentEvent` per period touched. It used to send the whole price to principal, which closed the loan with its interest still live. Anything above the debt is the house's and is recorded in `allocated_to_fees`, so the payment's buckets always add up to its `total_amount`; leaving the surplus unassigned made a payment unable to account for money it said it had received. `liquidate` and `sell` require `for_sale` — goods in custody are the customer's until a foreclosure says otherwise.
- **`allocate_oldest_first` in [allocation.py](apps/api-server/src/modules/finance/allocation.py) is the single ordering rule**, shared by `pay_interest` and the foreclosure sale. It is pure: it decides amounts, and each caller writes its own `PaymentEvent` rows with its own `payment_type`. Two copies of that loop drifting apart is how the same debt starts reporting two figures.
- **`POST /loans/{id}/close` with `force: true` needs a `reason`** (min 3 chars) whenever the loan still owes principal *or* interest, and stamps `force_closed_reason` / `force_closed_at` / `force_closed_by` on the row. Same reasoning as a payment reversal: forcing a close writes the balance off, and the audit table has no read path in the application, so without those columns the debt just stops being collectable with nobody's name on the decision. Zero principal is not "owes nothing" — a loan settled with `allow_with_unpaid_interest` still owes its interest. Nothing in the web client calls this endpoint; it is an API-only surface.
- **A pledge's `custody_code` is derived from its own row id** (`CUST-{id:05d}`), assigned after a `flush()` behind a temporary placeholder because the column is unique and not nullable. It used to be `count() + 1`, which breaks as soon as a pledge is deleted — and deleting a loan cascades to its pledges. With the counter behind, the next registration either hit a code that still existed, and the unique index turned every further attempt into a 500 that never cleared, or it landed in the gap and **reissued a label already printed on a customer's document**. Row ids are never reused.
- **Custody hand-back is never automatic.** `POST /collateral-items/{id}/release` and `POST /collateral-items/loans/{id}/release` flip `in_custody` → `released`, and both require the loan to owe *nothing* — zero principal **and** zero pending interest via `pending_interest_total_for_loan`. Principal alone is not enough: a loan closed with `force` can sit at zero principal with interest still owed, and returning the pledge then gives away the only leverage to collect it. Settling a loan only *offers* the hand-back, because handing over goods is a counter action — a customer may pay today and collect next week, and auto-releasing would make the custody report claim an empty vault. The offer is a checkbox in the principal collection form (shown only when the entered amount would actually free pledges, default off) plus a permanent action on the custody tab of `CollateralsView`; it is deliberately not a modal, since the payment flow already spends its one confirmation on the money. When a payment releases pledges, the receipt prints them with a signature line so the document doubles as the delivery record.
- Customers with loans or applications cannot be deleted — 409 `"related credit records"`; the frontend matches on that substring to show an archive-instead message.
- **A loan is blocked by *live* money, not by history.** `DELETE /loans/{id}` refuses (409) only while a non-reversed `Payment`/`PaymentEvent` exists, when the loan was renewed into another, or when a payment on it also touches another loan (unwinding one side would leave that payment describing money it no longer accounts for). Reversed rows do **not** block: a loan paid off by mistake, reversed, and then removed is the whole point — blocking it left operators with a phantom loan they could neither collect nor delete. Each refusal has its own message and its own store-mapped translation, because "cannot be deleted" gave no hint that reversing the payments first would work.
- When a loan *is* deletable the delete cascades to its `PaymentEvent`, `Payment`, `CollateralItem` and `InterestCharge` rows (children first — events reference both payments and charges), so the `delete_loan` audit entry carries a full snapshot: customer, amounts, rate, dates, every pledge with its custody code and value, every accrued period, and every reversed payment with its reversal reason. It is written **in the same transaction** as the delete — an audit row that can be lost while the delete survives reads as "this never existed".
- Use `get_local_date(db)` / `get_local_datetime(db)` (reads `GlobalSettings.timezone`, default `America/Bogota`) for "today" — not `date.today()`.
- **`GlobalSettings` is a single row, `id=1`**, created on demand by `_ensure_global_settings` — never query it as a collection. It is where portfolio-wide policy lives (`default_grace_days`, `interest_generation_lead_days`, `default_late_penalty_rate`, `timezone`, `date_format`, `currency_code`, plus the company identity printed on documents), so a knob that should apply to the whole book belongs here rather than as a new `Loan` column — that is exactly the mistake grace days made.

Export/import (`GET /backup/export`, `POST /backup/import`, admin only) discover tables and columns from `Base.metadata.sorted_tables` rather than a hand-written list, so **a new model column is carried automatically**. Keep it that way — never hardcode field lists in [backup/service.py](apps/api-server/src/modules/backup/service.py) or [backup/restore.py](apps/api-server/src/modules/backup/restore.py), or backups start silently losing data. Live password-reset tokens are the only redacted fields.

The import is a **full replace**, not a merge: it wipes every table and reloads from the archive in one transaction, so a mid-restore failure leaves the data untouched. Its guards are load-bearing — refuses on a schema-revision mismatch, on column drift, on a missing table, and on an archive without an active administrator; requires the typed phrase `REPLACE ALL DATA`; takes the interest-cycle advisory lock so the scheduler cannot write mid-restore; and realigns PostgreSQL identity sequences afterwards (without that, the next insert collides with a restored id). `validate_only=true` returns the plan without writing.

**The recurring backup takes that same archive on a schedule** — full spec in [docs/scheduled-backups.md](docs/scheduled-backups.md). The parts that are decisions rather than mechanics:

- **`BackupSettings` is a single row (`id=1`) and deliberately *not* part of `GlobalSettings`.** `GET /settings` takes plain `get_current_user`, so every authenticated role reads it; these columns hold the OAuth client secret and refresh token of the Google account the archives land in. They live behind the admin-only `/backup/*` routes and **no endpoint ever returns one** — `BackupScheduleRead` reports `drive_connected` and the account's email, never a value. This is the one exception to "portfolio-wide policy belongs in `GlobalSettings`", and the reason is the read permission, not the subject matter.
- **`backup_runs` is the only evidence the schedule works**, so every attempt writes a row with its error in full, and `run_backup` never raises for a destination failure — the failure *is* the result. There is deliberately no `last_status` cache on `BackupSettings`: a schedule that stopped in June and one that never ran look identical from outside, and a denormalised copy of that answer is one more thing that can disagree with it.
- **Whether a copy is due is derived from `backup_runs`, not from anything a worker remembers** (`is_backup_due` compares against `last_due_slot`). That is what makes a missed slot get taken: a droplet that was off at 2am copies as soon as it is back, and copies once. A failing slot is retried `MAX_ATTEMPTS_PER_SLOT` (3) times and then left until the next one — without the cap a revoked Drive token writes a row every fifteen minutes and buries the first failure, which is the row that says what broke. **Only `trigger='scheduled'` runs count**: a manual "back up now" is an extra copy, and letting it satisfy the schedule means a run at 1am silently cancels the 2am one.
- The scheduler is the same shape as the interest one (daemon thread per worker) but takes **its own lock id**, `BACKUP_CYCLE_LOCK_ID`. The connection handling both share now lives in `advisory_lock` in [tasks/locks.py](apps/api-server/src/infrastructure/tasks/locks.py); `interest_cycle_lock` stays a named wrapper because three callers must take that exact id.
- **Google Drive is OAuth 2.0 with `drive.file`, and a service account is not an option** — Google removed service-account storage quota in 2021, so the service account owns what it uploads, is charged against a quota of zero, and fails with `storageQuotaExceeded` even inside a folder shared with it; it only works against a paid Workspace Shared Drive. `drive.file` is non-sensitive (no Google verification) and grants access only to files the app itself created, which is also why the destination folder is **created by the app** rather than chosen: a folder it did not create is invisible under that scope. **The consent screen must be set to "In production"** — in "Testing" Google expires the refresh token after 7 days and the schedule fails silently.
- `drive_client_secret` and `drive_refresh_token` are in `REDACTED_COLUMNS`. An archive carrying them hands over the destination the archives are kept in, inside a file copied off the server by design. The cost is that a restore leaves Drive disconnected, so `_check_backup_destination` warns about it in the import analysis rather than letting the schedule quietly stop right after the event that proved it was needed.
- Retention deletes **only files matching the export naming pattern**, ordered by the timestamp *in the filename* rather than by mtime or by the whole name (the rest of the name is the company slug, so an operator renaming the company would otherwise reorder the copies). The destination folder is the operator's folder and may hold anything else.
- `BACKUP_SCHEDULER_ENABLED` / `_INTERVAL_MINUTES` / `BACKUP_LOCAL_DIRECTORY` are the only environment knobs, because they are deployment facts; everything an operator changes is in the database and edited from the settings screen. The interval is the schedule's precision. The local directory is the `backup_data` Docker volume — a copy written elsewhere in the container is discarded by the next deploy, and a copy on the droplet protects against a bad release, not against losing the droplet.

`Loan.interest_due`, `Loan.collaterals_count`, and the `CollateralItem.loan_*` properties issue queries via `object_session`, so they only work on session-attached instances and are N+1 by nature in list endpoints. When you need balances for many loans at once, call `pending_interest_for_loans` (fixed query count) instead of the per-row property.

### Frontend patterns

- **No Pinia/Vuex.** [platformStore.ts](apps/web-client/src/stores/platformStore.ts) is a module-level `reactive()` singleton exported as `usePlatformStore()`; [authState.ts](apps/web-client/src/modules/authentication/authState.ts) is the same pattern for the session.
- The store owns the shared entity cache (customers, loans, collateral, payments, settings) and calls `refreshAll()` after every mutation — a full 5-endpoint refetch, not a local patch. Mutations return `{ ok, messageKey }` for the caller to translate.
- **snake_case → camelCase mapping is manual** in the store's `mapCustomer`/`mapLoan`/`mapCollateral`/`mapPayment`/`mapGlobalSettings` functions, with `BackendXxx` interfaces mirroring API shapes. Adding an API field means touching the `Backend*` interface, the mapper, and `types/domain.ts`. Note `in_custody` ↔ `in-custody` is remapped, and customer `fullName` is split/joined into `first_name`/`last_name`.
- Payment/user/print/backup flows bypass the store and call `apiClient.request` directly (`PaymentsView`, `UsersView`, `CustomersView`, `InvoicePrintView`, `ScheduledBackupCard`) with snake_case bodies. [ScheduledBackupCard.vue](apps/web-client/src/components/ScheduledBackupCard.vue) is the whole recurring-backup UI, mounted in `SettingsView` — it also finishes the Google consent flow, which returns to `/settings?code=…`, and compares the `state` against what it put in `sessionStorage` before leaving. That comparison is what stops a crafted link from pointing the installation's backups at a stranger's Drive; do not drop it when moving the redirect elsewhere.
- Payments are listed in three places — `PaymentsView`'s history, the payments tab of the customer detail in `CustomersView`, and the loan payments table in `LoanDetailModal` — and all three delete through [PaymentReversalModal.vue](apps/web-client/src/components/PaymentReversalModal.vue), which owns the reason field, the minimum length, the request and the error display. Put the delete action anywhere new by mounting that component, not by copying the modal: the wording and the enforced minimum are what make a removal answerable the same way everywhere. `LoanDetailModal` refreshes the store itself and emits `payments-changed` so its parent can reload whatever it fetched separately.
- The two collection tabs in `PaymentsView` (interest, principal) are deliberately the same shape and share their moving parts: [useRowSelection.ts](apps/web-client/src/composables/useRowSelection.ts) owns the tick-a-row `Set` (and prunes ids whose row disappears — the hand-rolled version kept the previous customer's selection, which was harmless for interest but would move real money for principal), and [PaymentCollectionForm.vue](apps/web-client/src/components/PaymentCollectionForm.vue) owns the identical amount/method/suggested/print/submit footer, with each tab's summary lines passed through its default slot. Both tabs open with every row ticked and the amount prefilled to that total; typing in the amount field raises a `touched` flag that stops it re-syncing. Put new shared behaviour in those two, not in a third copy.
- **Destructive confirmations are one global modal, not a local `ref`.** [useConfirmDialog.ts](apps/web-client/src/composables/useConfirmDialog.ts) holds its state at module level (same singleton trick as the store), a single `<ConfirmModal>` is mounted once in [App.vue](apps/web-client/src/App.vue), and callers `await confirm(t('...'))` for a boolean — `LoansView`, `CustomersView`, `CollateralsView`, `PaymentsView` and `LoanDetailModal` all go through it. Because the state is shared, only one confirm can be open at a time; don't open a second from inside a resolved handler. Payment removal is the exception and belongs to `PaymentReversalModal` (above), which needs a typed reason rather than a yes/no.
- Long tables pair [usePagination.ts](apps/web-client/src/composables/usePagination.ts) with `Pagination.vue`; the composable resets to page 1 only when the source array's *length* changes, so a same-length re-sort keeps the current page.
- [api.ts](apps/web-client/src/services/api.ts) injects the bearer token, and on 401 logs out and hard-navigates to `/login`; it throws `new Error(await response.text())` so callers pattern-match on message substrings.
- Auth is JWT in `localStorage`; [router/index.ts](apps/web-client/src/router/index.ts) guards on `meta.requiresAuth` / `meta.guestOnly` / `meta.roles` and fetches `/auth/me` lazily.
- **i18n is mandatory**: all UI strings go through `vue-i18n` keys defined in [messages.ts](apps/web-client/src/i18n/messages.ts) — every key must be added to **both** the `en` and `es` blocks. Locale persists to `localStorage`. `t()` renders a *missing* key as the key itself, so a typo or an unmapped value silently ships raw text like `common.loading` to the user instead of failing anywhere. **`npm run check:i18n` is that check** ([scripts/check-i18n.mjs](apps/web-client/scripts/check-i18n.mjs)) and CI runs it beside `vue-tsc`: it fails on a key referenced but undefined, and on a key defined in one locale but not the other. It found six live ones — `common.notes` was printing the literal string onto a customer's receipt, and `common.confirmAction`/`common.accept` reached a Spanish-first team in English through a single-language fallback. **A `t('some.key', 'English default')` fallback is not a fix**: it hides the missing key from the reader in one language and from this check in both. Add the key to both blocks instead.
- `PaymentEvent.payment_type` is translated only through `paymentTypeKey()` in [utils/paymentTypes.ts](apps/web-client/src/utils/paymentTypes.ts). That map used to be copy-pasted into `PaymentsView`, `CustomersView` and `InvoicePrintView`, which had each drifted out of sync with the API — `partial_interest_payment`, `full_settlement` and `collateral_sale` were missing from two of them and leaked out untranslated. Adding a type server-side means adding it there, in one place.
- **Styling is plain CSS with design tokens**, no Tailwind. All tokens (`--accent`, `--surface`, `--radius`, `--shadow-*`, `--transition`) and shared classes (`.modal-backdrop`, `.form-section`, `.empty-state`, tables, buttons) live in [main.css](apps/web-client/src/assets/main.css). Reuse tokens and existing classes; don't introduce hardcoded colors or a CSS framework. **[DESIGN.md](DESIGN.md) is the spec** — it records what each token is for and, more usefully, which defaults this system refuses. Three things there are load-bearing rather than taste:
  - **Primary actions are `--ink`, not `--accent`.** Every table row carries an action, so an accent-coloured button on each one leaves the accent meaning nothing. `--accent` is spent only on orientation: active nav, focus, selection, sort, links.
  - **Figures go through `--font-mono` with `tabular-nums`** (`.num`, `.num-strong`, `.code`, and automatically on any `td.text-right`, since a right-aligned cell in this app is always a figure). Proportional digits move the thousands place between rows, and these screens are mostly columns of pesos.
  - **A token that does not exist is worse than a hardcoded value**, because `var(--nope, #2563eb)` silently ships the fallback. `--color-primary`, `--color-text` and `--color-text-muted` were all referenced and never defined, which left three controls painting in the pre-redesign palette. Same failure in the other direction: `.page-header-actions`, `.fw-bold`, `.text-warning-dark`, `.spinner-small`, `.mt-24` and `.notice-info` were in the markup with no rule anywhere, so they styled nothing at all.
- **Phones are a supported scene, and below 768px tables restack into card lists.** Every `<td>` carries `:data-label="t('...')"` reusing the *exact* `t()` expression from its matching `<th>`; the `<thead>` hides and `td::before { content: attr(data-label) }` reattaches each heading to its value. A hardcoded string in a `data-label` is an untranslated string on a phone that `check:i18n` cannot see, because it is not a key. Cells with no `data-label` (actions, checkboxes) become full-width blocks — that is deliberate, not an omission. A table without `data-label`s keeps horizontal scroll, so the pattern degrades rather than breaks. Adding a table means adding the labels.
- **Interest allocation is shown, not chosen.** `POST /payments/interest` allocates oldest-charge-first across the customer's whole book and ignores `selected_charge_ids` by design, so the interest tab has no checkboxes: it renders the allocation the server will perform, and the confirmation names the periods that will actually be closed. It used to carry a checkbox column while sending `pay_all_pending: true` with an empty selection, so the last screen before money moved asserted a destination that was not where the money went. The **principal** tab keeps its checkboxes — there the client's selection *is* honoured (CLAUDE.md's "two deliberate asymmetries"). Do not make the two tabs symmetrical.
- **Light and dark both ship, and `system` is the third real state**, not a synonym for light — see [useTheme.ts](apps/web-client/src/composables/useTheme.ts). The *preference* is stored; the *resolved* value is written to `data-theme` on `<html>` by an inline script in `index.html` before first paint, and `useTheme` re-applies the same rules on mount so the two cannot disagree. That is why the dark palette is a plain `[data-theme='dark']` block rather than `prefers-color-scheme`: the media query cannot express "the operator chose light on a machine set to dark". **The four printed documents pin themselves to the light tokens** in `InvoicePrintView`'s own `.print-container` rule — browsers drop backgrounds when printing, so a dark receipt would put near-white text on white paper. **`npm run check:contrast` measures every foreground/background pair in both themes** against WCAG AA and CI runs it; it caught `--placeholder` shipping at 3.4:1 behind a comment claiming 4.6:1.
- **`getCustomerName` returns `string | null`, never a sentinel.** It used to answer `'__UNKNOWN_CUSTOMER__'`, which every caller had to know to translate — two views carried an identical guard and a third that forgot would have printed that literal on screen. Resolve a name through [useCustomerLabel.ts](apps/web-client/src/composables/useCustomerLabel.ts), which is the one place that decides what an absent customer reads as.
- **Money and dates are formatted in exactly one place each**: [utils/currency.ts](apps/web-client/src/utils/currency.ts) and [utils/date.ts](apps/web-client/src/utils/date.ts), both module-level singletons set from `GlobalSettings` by the store. `formatCurrency` had been written out in nine files and drifted: eight grouped with `es-MX` (`COP 1,250,000`) while the printed receipt used `es-CO` (`$ 1.250.000`), and `CurrencyInput` grouped with `en-US`, so an operator typed an amount in one format, read it back in a second and handed over a document in a third. **Locale follows the currency, not the interface language** — switching the UI to English must not change what a figure looks like. Two views had also re-implemented `formatDateDMY` with a hardcoded `DD/MM/YYYY`, making them the only screens where `GlobalSettings.dateFormat` did nothing.
- **Form controls are wrapped, not native.** Money goes through [CurrencyInput.vue](apps/web-client/src/components/CurrencyInput.vue) (thousands separators in, a `number` out), dates through [DateInputField.vue](apps/web-client/src/components/DateInputField.vue) (text field plus calendar popover, formatting via `utils/date.ts`), and **every** dropdown through [CustomSelect.vue](apps/web-client/src/components/CustomSelect.vue) — there is not one raw `<select>` left in `views/` or `components/`, so adding one is what breaks the visual consistency. `CustomerAutocomplete`, `PasswordInput` and `StatCard` are the other shared controls. Rates, counts and other bare numerics stay plain `<input type="number">`.
- Date display/parsing goes through [utils/date.ts](apps/web-client/src/utils/date.ts), whose global format is set from `GlobalSettings.dateFormat` on load. Send ISO (`YYYY-MM-DD`) to the API via `toIsoDate`.
- UI conventions from `.agents/skills/`: create/edit forms belong in modals (or a dedicated route), triggered from `PageHeader`'s `#actions` slot — never inline forms above a table; always render an `.empty-state` instead of a bare table header; group fields in `.form-section` with a title; mobile-first with AA contrast and visible focus states.

### Design skills

Two third-party skill packs are vendored under `.claude/skills/`, which is where Claude Code discovers them — the four house skills in `.agents/skills/` stay where they are and remain the authority on *this* project's UI conventions:

- **impeccable** (`/impeccable <command>`, Apache 2.0) — design review and refinement. It also ships a deterministic detector: `npx impeccable detect apps/web-client` scans for 59 anti-patterns with no model in the loop, which makes it the one design check that can run in CI.
- **taste-skill** (MIT) — four of its thirteen skills are installed: `redesign-existing-projects`, `design-taste-frontend`, `minimalist-ui`, `full-output-enforcement`. The image-generation and alternate-direction skills (brandkit, imagegen-*, brutalist, stitch, gpt-taste, v1) are deliberately **not** installed; they answer questions this repository does not ask. `skills-lock.json` pins what was taken so the set is reproducible.
- **ui-ux-pro-max** (MIT) — a searchable local database of ~98 UX guidelines plus styles, palettes and font pairings, queried through `python .claude/skills/ui-ux-pro-max/scripts/search.py "<query>" --domain ux`. **Use the `ux` domain and the Pre-Delivery Checklist; do not use `--design-system` here.** That generator is built for landing pages: asked about this app it returned a "Real-Time / Operations Landing" *page pattern*, a style whose own record reads "Best For: Fashion, architecture, portfolios, luxury brands, editorial", `font-size: clamp(3rem, 10vw, 12rem)`, weight 900, and a generic blue palette with Fira Code — which would undo the system in DESIGN.md wholesale. Its sibling skills are not installed: `ui-styling` is built on shadcn/ui + Tailwind and would push against the no-Tailwind decision above, and `banner-design` / `brand` / `slides` / `design` (logo generation) answer questions a back office does not ask.

Its checkable rules are worth re-running after UI work, and they found real defects the other two packs missed: search inputs carrying a placeholder as their only label, a `ⓘ` character standing in for an icon in fifteen places, and an icon-only row action with no accessible name.

**This app is an Operate surface, and that is what settles the disagreements between those packs and this repository.** impeccable's own mode table puts admin dashboards and data tables under Operate, where "scanability, consistency, native expectations and the real usage scene outrank expression" — so the parts of taste-skill written for landing pages do not apply here and must not be imported by reflex: no background photography or `picsum.photos` placeholders, no parallax or scroll choreography, no doubled whitespace (density is correct for a ledger), and the left sidebar stays. Where a skill contradicts a decision recorded in this file, **this file wins** — the clearest case is modals, which impeccable calls "usually laziness" while the convention above requires them for create/edit forms. A skill describes a general aesthetic; the notes here describe why this system is shaped the way it is.

Both packs write scratch state to `.impeccable/`; the `# impeccable-ignore-start` block in `.gitignore` keeps the ephemeral half out of the repository and the shared half (`config.json`, `design.json`, `critique/*.md`) in it. [PRODUCT.md](PRODUCT.md) carries the durable product context the commands read; [DESIGN.md](DESIGN.md) plus `.impeccable/design.json` carry the visual system.

**One detector rule is waived, and the reason is written into [.impeccable/config.json](.impeccable/config.json) rather than left implied.** `flat-type-hierarchy` wants ≥1.25 between adjacent type steps; impeccable's own `reference/operate.md` prescribes 1.125–1.2 for product UI, because these screens carry far more type elements and exaggerated contrast reads as noise. Forcing the ratio would put form labels at 11px or input values at 17.5px. `detector.ignoreRules` only holds rule names, so the justification lives in a `$comment` beside it — a waiver nobody can trace is indistinguishable from someone silencing an inconvenient rule. Remove it if the type scale is ever reworked.

### Printable documents

All four printable documents are one component, [InvoicePrintView.vue](apps/web-client/src/views/InvoicePrintView.vue), on a single route `/print/invoice/:type/:id` that sits **outside** `AppLayout` (no nav chrome) and calls `window.print()` ~500 ms after mount. `:type` selects the document — `payment` (receipt), `loan` (loan statement), `customer` (customer statement), `history` (payment history) — and the `isLoan` branch is the fallback, so an unknown `:type` renders a loan statement rather than erroring. Callers are plain `<a target="_blank">` links (or `router.push` right after creating a loan/payment) in `LoansView`, `PaymentsView`, `CustomersView`, and `LoanDetailModal`.

Every document is dated the day it is printed; the dates that belong to the fact itself — the loan's disbursement, the payment's date — are printed in the body, so a reprint cannot pass itself off as having been issued back then. The loan document's "payment day" is the day-of-month of the disbursement, which is what anchors the billing cycle — it used to print `dueDay`, and once grace days moved to a global setting that read "payment day: 0 of each month". It is derived by `billingAnchorDay()` in [utils/date.ts](apps/web-client/src/utils/date.ts), shared with `LoanDetailModal`'s pill; anywhere else that wants to show a loan's billing day should call it rather than read `dueDay`, which no longer means anything to a customer.

There is **no HTML-rendering print endpoint on the backend**. The view reads the store for entity data and fetches figures directly: `/payments/customers/{id}/principal-context` (per-loan payoff figures), `/payments/customers/{id}/interest-pending` (the pending periods behind them), `/payments/{id}/allocations` (the receipt's distribution breakdown) and, for `history`, `/payments/customers/{id}/history`. For a `payment` receipt those calls run *after* the payment, so the figures printed are the balances remaining afterwards. A failed fetch is swallowed — the document still prints with whatever the store held.

Because the view destructures those responses by exact field name, renaming one server-side prints zeros instead of failing. [tests/test_printable_statements.py](apps/api-server/tests/test_printable_statements.py) exists solely to pin that contract (field names plus the arithmetic) — update it in the same change as any rename, and don't treat it as a redundant duplicate of the payments tests.

`GET /payments/{id}/allocations` exists because `Payment` alone cannot explain itself: it stores only per-bucket totals and its `loan_id` is just the *first* loan touched, while one payment routinely settles several `InterestCharge`s across several loans (allocation is oldest-first). The endpoint returns the `PaymentEvent` rows in `id` order — the real order the money was applied — enriched with each charge's own amount and due date, so the receipt can print "this $100k covered invoice A in full and invoice B partially". `fully_covered` is derived from the `partial_interest_payment` type stamped at creation, not recomputed. Payments made through the plain `POST /payments` path have no ledger rows, so the list comes back empty and the receipt falls back to the per-bucket summary table.

The `loan` document also prints the pledged items (custody code, description, appraised value, plus an appraised total) from `state.collateralItems` filtered by `loanId` — no extra fetch. Columns appear only when they carry information: `item_type` and `serial_number` default to `general`/empty and have no form field anywhere; `status` is `in_custody` for every item on a freshly issued document, so it shows up only on a reprint after a foreclosure/release/sale.

**`physical_condition` is deliberately not printed.** It defaults to `"good"`, no UI collects it, and `CollateralUpdate` omits it, so it can never be edited — every row in a real database carries the default. Printing it would assert on a customer-facing document that the item was inspected and found in good condition when no such assessment was ever recorded. The test for whether a defaulted field may be printed is whether its fallback reads as "nothing recorded" (empty serial, `general` type — safe to hide) or as a substantive claim (`good` — must not be shown). If a form field for it is ever added, printing it becomes legitimate.

`CollateralItem.status` is a plain varchar, not an enum, but **it is not an editable field**: `PUT /collateral-items/{id}` accepts `status` only when it matches what the pledge already has, and answers 400 otherwise. It used to write `payload.status` straight through, so a loan officer could set `released` on the security of a loan with its full principal outstanding — walking past `_assert_loan_fully_settled`, the check that makes the collector-accessible release routes safe — and any string at all was stored, including ones no screen can render. Custody moves through `release`, the foreclosure, `liquidate` and `sell`, each of which checks something first. The store no longer sends the field at all, and the edit modal in `CustomersView` shows it as a read-only `.form-static-value`. The values endpoints actually produce are `in_custody` (create), `for_sale` (foreclosure), `released`, `liquidated` and `sold`. **`returned` is written only by [seed.py](apps/api-server/src/infrastructure/persistence/seed.py) — no endpoint ever sets it**, yet it is carried in `types/domain.ts` and labelled in `CollateralsView`, sitting confusingly next to the real `released`. Treat it as demo-data residue rather than a domain state.

Print styling is deliberately restrained — whitespace carries the structure. One accent colour, one emphasis weight (`.balance-value`), one hairline, `.doc-section` + `.section-title` for every block in all four documents. No panel fills, no header-row fills, no bordered pills. Columns that would be all zeros are dropped rather than printed empty, and `@media print` forces `print-color-adjust: exact` (browsers drop backgrounds, which would erase every status pill) plus `table-header-group` so long tables repeat their header. When adding to these documents, reuse those two classes instead of introducing another sectioning device.

## Tests

`pytest` only, in `apps/api-server/tests/`, one file per module. [conftest.py](apps/api-server/tests/conftest.py) builds a fresh app per test with `get_db` overridden, plus `auth_headers`, `create_customer`, and `create_loan` fixtures; tests exercise endpoints end-to-end through `TestClient`. The scheduler is disabled in the `app` fixture.

A few files guard cross-cutting invariants rather than one module, and are easy to mistake for duplicates: `test_printable_statements.py` (frontend field contract, above), `test_interest_scheduler_lock.py` (multi-worker cycle lock), `test_payment_reversal.py`, `test_loan_status.py` (the automatic `active` ↔ `overdue` job), `test_interest_accrual_policy.py` (accrual in arrears, the frozen penalty, invoiced periods being immutable and undeletable, a backlogged period billed on the principal it carried, no penalties on a foreclosed loan), `test_renewal.py` (what a renewal must carry and must stop carrying twice), `test_collateral_sale.py` (foreclosure proceeds landing on the whole debt), `test_custody_and_access.py` (vault permissions, custody codes, the last-administrator guard), `test_interest_advances.py` (the customer-wide advance pool: consumed oldest-first across that customer's loans, keeping a covered loan out of `overdue`, and never reaching another customer's debt), `test_startup_guards.py` (what `assert_production_secrets` must refuse and — just as deliberately — what it must let through), `test_password_reset_email.py` (the mailer: an installation with no credentials still completing the flow, a send failure never reaching the caller, response parity between a known and an unknown identifier, and the send staying off the request path), `test_forced_closure.py`, `test_backup_import.py` (the full-replace guards) and `test_scheduled_backups.py` (the recurring backup: slot arithmetic, a slot the server slept through, the retry cap, a manual copy not satisfying the schedule, retention never touching a foreign file, and no credential ever leaving the API or entering an archive).

The engine is **in-memory SQLite by default**, or PostgreSQL when `TEST_DATABASE_URL` is set — CI sets it, so the suite runs on both. Backend code must therefore stay SQLite-compatible (no PG-only SQL outside the guarded bootstrap). To reproduce the CI run locally:

```bash
docker compose up -d postgres
TEST_DATABASE_URL=postgresql+psycopg://<user>:<pass>@localhost:5432/pawn_loan_db pytest -q
```

## CI, migrations, and branching

- **Quality checks** ([quality-checks.yml](.github/workflows/quality-checks.yml)) gate PRs into `main`/`develop`: `ruff check .` + `pytest` on PostgreSQL, and `vue-tsc` on the web client. Run all three locally before pushing. Migration scripts are excluded from ruff (`extend-exclude` in [pyproject.toml](apps/api-server/pyproject.toml)).
- **The linter is pinned exactly (`ruff==0.16.0`) and its rule set is spelled out (`select = ["E4", "E7", "E9", "F"]`)** — both deliberately, and both in [pyproject.toml](apps/api-server/pyproject.toml). An unpinned linter fails CI on an unrelated day because a new release changed the defaults, which is how 0.16 arrived with flake8-bugbear and B008 rejecting FastAPI's `Depends(...)` argument defaults. Widen `select` on purpose when you want a rule; never acquire rules by bumping the version.
- **Alembic migration guard**: any PR touching `models.py` or `src/domain/enums/*.py` must include a new file in `apps/api-server/alembic/versions/` or CI fails. Generate it with `alembic revision --autogenerate -m "..."` before pushing.
- **GitFlow guard**: PRs into `main` are only accepted from `release/*`, `hotfix/*`, or `develop`. Work lands on `develop` first.
- Merging to `main` auto-tags `vX.Y.Z` (version derived from the branch name), builds both images and pushes them to GHCR, then deploys to DigitalOcean via `docker-compose.prod.yml`. See [docs/ci-cd-digitalocean.md](docs/ci-cd-digitalocean.md) and [docs/deployment-digitalocean.md](docs/deployment-digitalocean.md).
- **Production configuration is versioned; only three values are secrets.** [deploy/digitalocean/production.env](deploy/digitalocean/production.env) holds every non-secret production value and [remote_deploy.sh](deploy/digitalocean/remote_deploy.sh) renders `.env.production` on the droplet from it plus `POSTGRES_PASSWORD`, `JWT_SECRET_KEY` and `ADMIN_PASSWORD` (GitHub secrets), composing `DATABASE_URL` so the password exists in one place rather than in a second literal copy inside a URL. A new production knob belongs in that file, not in a secret and not in a hand-edited file on the server: `.env.production` is generated on **every** deploy, so editing it over SSH is lost work, and a value that only exists there cannot be reviewed or rolled back. The repository is public — a secret added to `production.env` is published.
- **The deploy procedure has exactly one copy**: `remote_deploy.sh`, reached through [.github/actions/deploy-to-droplet](.github/actions/deploy-to-droplet/action.yml), which both `release-tag-and-deploy.yml` (on merge) and `deploy-droplet.yml` (manual, and the rollback path) call. The release path and the rollback path being able to do different things is the failure this shape exists to prevent. Nothing is ever built on the droplet — it pulls the images the release job published, which is what lets a 1 GB box run this at all.
- **`VITE_API_BASE_URL` is a build input, and it is relative (`/api/v1`).** Vite inlines it into the bundle, so it cannot be changed on the droplet; Caddy serves the SPA and the API on one origin, so a relative value makes the image independent of the hostname and a domain change needs no rebuild. It used to be an absolute URL in a GitHub secret, which meant the deployed frontend kept calling the *previous* domain until someone remembered to rebuild. It is read from `production.env` at build time.
- **`index.html` is served `no-cache`; everything under `/assets/` is `immutable` for a year** ([nginx.prod.conf](apps/web-client/nginx.prod.conf)). Vite fingerprints the bundles, so a stale asset can never be served for new content — but `index.html` is the only file that knows which fingerprint is current, and a cached copy pins the browser to the previous release. That is not theoretical: after the deploy that made the API base URL relative, browsers holding the old document kept calling a hostname that no longer resolved, and `LoginView` reported it as invalid credentials. Which is also why only a **401** prints `auth.invalidCredentials` — anything else is `auth.serviceUnreachable`, because "wrong password" is a claim about the server's answer, and a request that never arrived has none.
- **Every request is logged once, by Caddy** ([Caddyfile](deploy/digitalocean/Caddyfile)), in JSON on stdout: it is the only component that sees each request with its real client IP, since nginx and the API sit behind it. `docker compose logs -f reverse-proxy` is where "did that request even arrive?" gets answered. All services cap their logs at 10 MB × 3 via the `x-logging` anchor in `docker-compose.prod.yml` — the json-file driver is unbounded by default, and turning on access logging without a cap is how the disk fills a month later.
- **`DOMAIN` must resolve to the droplet before the deploy that changes it.** Caddy requests a Let's Encrypt certificate for exactly that name and issuance fails on a name that does not point there yet — and since it is the only site address, the app is unreachable until it does. Create the DNS record first, then change the value.
- `LoanType`/`LoanStatus` use native PG enums, so adding a value needs a migration that alters the type; `UserRole` uses `native_enum=False` (varchar).

The functional spec and business-rule table live in [.github/loan-management-system-requirements-and-software-design.md](.github/loan-management-system-requirements-and-software-design.md).
